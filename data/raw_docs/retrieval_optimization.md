# RAG 检索优化与召回

RAG 系统的回答质量很大程度取决于检索质量。大模型只能基于传入的上下文生成答案，如果检索阶段没有找到相关资料，后续 Prompt 写得再好也很难回答准确。因此，检索优化的目标不是让分数看起来更高，而是让真正有用的 chunks 更稳定地进入最终上下文。

向量检索通常使用 Top-K 参数控制返回数量。Top-K 表示从向量数据库中取回最相关的 K 个文本块。较小的 Top-K 可以减少噪声，让答案更聚焦；较大的 Top-K 可以提升召回，降低漏掉关键资料的概率。当前项目在 RAG 问答中使用 top_k 控制最终上下文数量，在 Hybrid Search 中还使用 candidate_k 扩大候选召回范围。

召回和精度需要平衡。召回强调“有没有把相关资料找回来”，精度强调“返回结果里无关内容少不少”。例如用户问“Rerank 的作用是什么”，如果 Top-K 结果全部来自 RAG 入门文档而没有重排序内容，说明召回不足；如果结果里混入和向量检索主线无关的资料，说明精度不足。优化检索时要同时观察这两个方向。

影响检索效果的因素主要包括：

- chunk_size：文本块过小会缺少上下文，过大会混入多个主题；
- chunk_overlap：适当重叠可以避免关键信息被切断；
- Embedding 模型：模型要适合中文语义和当前领域；
- 文档结构：标题、小标题和列表能帮助文本块保留主题信息；
- Top-K 和 candidate_k：候选数量决定召回范围；
- 去噪和筛选：无关主题进入知识库会干扰检索。

当前项目的一个优化思路是先进行基础向量检索，保证语义相关结果的稳定性；再使用 Hybrid Search 扩大候选范围；最后用 Rerank 模型对候选 chunks 重新排序。这个流程把“召回更多可能相关内容”和“筛选更适合回答的问题片段”拆成两个阶段，适合教育资料问答这种要求依据明确的场景。

检索优化还需要日志和评测支持。项目会记录检索到的 chunk_id、source、distance、dense_score、sparse_score、hybrid_score 和 rerank_score。通过这些日志，可以分析某个问题为什么召回失败，是向量检索没有命中，还是 Hybrid Search 引入噪声，或者 Rerank 没有把正确片段排到前面。持续观察失败案例，是改进 RAG 系统的重要方法。
