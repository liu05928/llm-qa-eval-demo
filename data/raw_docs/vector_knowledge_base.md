# 向量知识库构建流程

向量知识库是把原始文档整理成“可被语义检索的资料库”的过程。它不是简单地把文件放进目录，而是要经过文档读取、文本切分、Embedding 向量化、向量数据库写入和检索验证等步骤。当前项目的知识库主线围绕教育资料问答，因此适合加入概念清晰、主题集中的 Markdown 文档。

在当前项目中，原始资料放在 `data/raw_docs/`。文档读取模块会读取这些 Markdown 文件，并保留文件名作为 source。随后文本切分模块会把长文档切成多个 chunks。每个 chunk 都有自己的 chunk_id，例如某个文件的第一个片段会生成类似 `embedding_intro_001` 的编号。chunk_id 的作用是让检索结果能够追溯到具体片段，方便日志分析、页面展示和答案引用。

切分后的 chunks 会保存到 `data/chunks/chunks.json`。向量库构建脚本会读取这个 JSON 文件，提取每个 chunk 的 content，调用 BAAI/bge-m3 生成 Embedding，然后写入 ChromaDB。写入时通常会保存三类信息：文本内容、向量表示和元数据。文本内容用于拼接 RAG 上下文，向量表示用于相似度检索，元数据用于显示来源和定位片段。

适合进入向量知识库的文档应满足以下条件：

- 主题和系统定位一致，例如 RAG、Embedding、向量数据库、检索优化；
- 每篇文档有明确标题和小标题，便于切分后仍保留语义；
- 内容不宜过度发散，一个段落最好只讲一个技术点；
- 避免加入和当前向量检索主线关系不大的扩展主题；
- 避免大量代码堆叠，优先写清楚概念、流程、输入输出和使用场景。

向量知识库的质量会影响 RAG 的最终回答。若原始文档主题混杂，检索阶段可能召回无关 chunks；若文档过短，模型可能缺少足够上下文；若文档过长，切分后可能产生重复或边界模糊的问题。对于教育资料 RAG，推荐把每个技术主题整理成独立 Markdown 文件，让每个 chunk 都能回答一个相对完整的问题。

构建完成后，需要用典型问题验证检索结果。例如询问“什么是 Top-K 检索”“Hybrid Search 为什么能提升召回”“Rerank 在 RAG 中解决什么问题”。如果返回的 chunks 能稳定命中相关文档，说明向量知识库的主题覆盖和切分质量比较合适。
