# Embedding 向量化入门

Embedding 是 RAG 系统中连接“自然语言文本”和“向量检索”的关键步骤。它的作用是把一段文本转换成一组数字向量。向量不是给人直接阅读的内容，而是给向量数据库和相似度算法使用的表示方式。语义越接近的文本，在向量空间中的距离通常越近；语义差异越大的文本，距离通常越远。

在当前教育资料 RAG 项目中，文档会先被读取并切分成 chunks。每个 chunk 的正文会交给 Embedding 模型生成向量，然后和 chunk_id、source、content 等信息一起写入 ChromaDB。用户提问时，问题本身也会被同一个 Embedding 模型转换成查询向量。系统再用查询向量去匹配知识库中的文本块向量，找出最相关的 Top-K 片段。

本项目使用的向量模型是 BAAI/bge-m3。bge-m3 适合中文和多语言语义表示，常用于 RAG 检索、文本相似度计算和问答系统。对于教育资料问答来说，它可以把“什么是向量数据库”和“向量库有什么作用”这类表达不同但语义接近的问题映射到相近的向量位置，从而提升召回效果。

Embedding 的质量会直接影响检索质量。如果文本块太短，向量可能缺少上下文；如果文本块太长，向量可能混合多个主题，导致检索结果不够聚焦。因此当前项目在切分阶段使用固定 chunk_size 和 chunk_overlap，让相邻文本块保留一定重叠，减少关键信息被切断的风险。

构建向量知识库时要注意几个问题：

- 文档和问题必须使用同一个或兼容的 Embedding 模型；
- 文本块内容应尽量围绕一个主题，避免一个 chunk 同时讲多个无关概念；
- 向量维度必须和向量数据库集合配置一致；
- 空文本、重复文本和噪声文本会降低检索质量；
- 更新原始文档后，需要重新切分并重建向量索引。

在 RAG 中，Embedding 不负责生成答案，它只负责把文本变成可比较的语义表示。真正的回答生成发生在检索之后：系统把 Top-K 检索结果拼接成参考上下文，再交给大模型生成最终回答。因此，Embedding 的核心价值是提高“找资料”的准确性，而不是直接回答用户问题。
